## 2 P14：资源清单的编写 1

### 2.1 课程讲解主线

**清单的层次与对象结构（00:04–01:29）。** 先看 YAML 的缩进层级，列出 apiVersion、kind、metadata、spec、status。课程随后区分需要用户声明的内容和集群维护的状态。理解重点是：清单描述一个对象的身份与期望，API Server 接受对象后，集群再逐步落实期望。

**为什么有 API 组和版本（01:29–08:47）。** 讲师用教务系统举例：多个业务堆在同一程序中，改动公共代码可能影响其他功能；拆分业务后，各部分可以有自己的演进节奏和接口版本。随后回到 Kubernetes 的 API 分组、版本与资源类型。这里的微服务例子是在解释“拆分职责与接口演进”，并不等于 Kubernetes 的每个 API 组一定对应一个独立微服务部署。

**用集群发现可用 API，而非死记清单（09:22–16:24）。** 演示虚拟机启动、组件逐步就绪；再用 `kubectl api-versions` 查看服务端公开的组和版本，比较核心组 `v1` 与带组名的 `apps/v1`。用 `kubectl explain pod` 和 `kubectl explain deployment` 找到资源说明、字段和版本信息。课程的 Docker、cri-dockerd 启动链属于其演示环境。

**kind、metadata、spec、status 分别回答什么（16:29–22:51）。** kind 是资源类别，metadata 给对象起名、指定命名空间和标签；spec 表达期望，status 表达观察到的现实。讲师用“对孩子的期望与实际成绩”类比两者差异。这正好衔接用户已经提出的疑问：Pod 对象可以已创建，而节点上的应用容器还没运行起来。

**逐层查询字段并提交一个 Pod（22:53–31:10）。** `kubectl explain pod.spec`、`kubectl explain pod.spec.containers` 逐层深入，辨认字段类型和必需项。示例 Pod 有两个应用容器，一个提供网页，一个通过 BusyBox 执行休眠保持运行。最后用 vim/vi 保存 YAML，`kubectl create -f` 提交；此时创建成功的含义是对象被接受，运行结果留到 P15 查询。

### 2.2 核心区别与需要修正的说法

- **常见对象结构 ≠ 所有资源一律有五项。** 课程开头把五个字段称为必需，随后又解释 status 由集群生成。普通声明清单不填写 status；更不能把 Pod 的结构套到所有对象，ConfigMap 使用 data/binaryData 而没有 spec。参见 [官方 ConfigMap 对象结构](https://kubernetes.io/docs/concepts/configuration/configmap/)。
- **API 版本 ≠ Kubernetes 产品版本。** `apps/v1` 不是“集群 v1”；它属于资源接口的版本。`api-versions` 查看可用组/版本，`api-resources` 才进一步列出资源种类及其作用域。新接口版本也不意味着所有场景都一定性能更好。
- **字段嵌套 ≠ 新建一个 Kubernetes 对象。** `spec.containers` 是 Pod 对象内部的列表，不能把其中每个字段称作一个独立可查询的 API 资源。
- **省略 namespace 不一定落到 default。** kubectl 可以使用当前 context 中的命名空间，`-n` 也会影响请求；没有其他指定时才通常落到 default。参见 [官方命名空间请求与上下文设置](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/#setting-the-namespace-for-a-request)。
- **同 Pod 不默认共享 PID namespace。** 28:35–28:48 将网络、IPC、PID 一并作为默认共享内容；进程命名空间共享需要显式设置 `spec.shareProcessNamespace: true`。同 Pod 能用 localhost 通信，不意味着默认能用 ps 看见彼此进程。参见 [官方进程命名空间共享](https://kubernetes.io/docs/tasks/configure-pod-container/share-process-namespace/)。

### 2.3 与已有经验和 v1.22.2 环境的衔接

可把 YAML 看成向平台提交的配置声明，类似运维配置文件；但保存文件本身不会改变集群，需要通过 kubectl 提交。`spec` 类似服务配置中的目标，`status` 类似服务管理器回报的观测状态，两者不是同一份静态配置。

本项目 Pod 仍用 `apiVersion: v1`，Deployment 用 `apps/v1`，与本节的现代写法一致。课程提及旧版本 Deployment 接口时，不要直接按“1.15 及以前都写 extensions/v1beta1”记忆：旧 beta 接口自 v1.16 停止提供，`apps/v1` 自 v1.9 已可用。参见 [官方 Deployment API 迁移说明](https://kubernetes.io/docs/reference/using-api/deprecation-guide/#deployment-v116)。本项目运行时为 containerd，不能照搬 Docker → cri-dockerd 的服务依赖。

## 3 P15：资源清单的编写 2

### 3.1 课程讲解主线

**从对象存在读到容器状态（00:00–03:58）。** 接上节创建的 Pod，观察 READY 从 0/2 到 2/2，查看 STATUS、RESTARTS、AGE。随后用不同 Namespace 查询 Pod，再用同样的 `-n` 查询 Node，说明 Pod 是命名空间级资源，Node 是集群级资源。集群级资源并不是在每个 Namespace 中各有一份。

**从 Kubernetes 对象找到节点容器（04:07–10:51）。** 介绍 `-A`/`--all-namespaces`、`-o wide`；通过 Pod IP 和 NODE 确认运行位置，再到演示环境的 Docker 中查看容器。将 pause、应用容器按 Pod 归组，访问网页，再进入容器修改网页验证访问到的是同一应用。

**建立基本运维命令集（11:01–20:37）。** `kubectl exec` 可以通过 Kubernetes 入口对指定 Pod 的指定容器执行命令；`-i` 传递标准输入、`-t` 分配终端、`-c` 指定容器、`--` 分隔远端命令。接着学习 `--show-labels` 显示标签，`-l app` 与 `-l app=myapp` 筛选对象，以及 `logs -c` 获取容器日志。后半段重整一张常用命令表。

**休眠结束为什么出现 RESTARTS（20:41–24:03）。** BusyBox 的前台命令 sleep 3600 结束，容器随主进程退出；默认 restartPolicy 下 kubelet 会再启动该容器。课程再引出控制器：直接创建的 Pod 被删除后，不会因 restartPolicy 自动补回；控制器可以根据期望创建新的 Pod。这是用户此前已经观察到的 RS 补建现象的另一面。

**用端口冲突引入排错（24:09–31:12）。** 复制清单，将第二个容器也改成网页应用，两个 Nginx 默认都想监听同一 Pod 网络环境下的 80 端口。先用 describe 看调度、镜像拉取、创建、启动和 BackOff 等事件，再用各容器的 logs 查错；第二个应用出现地址已占用。课程演示证明多容器 Pod 需要协调端口，而不是简单把两个独立 docker run 的配置放在一起。

### 3.2 核心区别与需要修正的说法

- **READY 计数、STATUS、Pod phase 不同。** 0/2 是应用容器就绪数，不含 pause，也不是节点数。kubectl 的 STATUS 是便于排查的展示，不能把 CrashLoopBackOff 等全部当成 Pod 的 phase。
- **容器重启 ≠ Pod 重建。** 课程说“重建”时，多数是在解释同一 Pod 内新的容器实例；应同时观察 Pod UID 和 containerID，避免以为 RESTARTS 增加就一定生成了新 Pod。课程“两个容器别一起死就能恢复”的限制也不准确；是否重试主要看 restartPolicy 和运行条件。[v1.22 官方生命周期说明](https://raw.githubusercontent.com/kubernetes/website/release-1.22/content/en/docs/concepts/workloads/pods/pod-lifecycle.md)明确把此策略限定为同节点的容器重启。
- **pause/sandbox ≠ initContainers。** 07:49 附近把基础设施容器称作“初始化容器”容易混淆。P16/P17 的 initContainers 是用户在 Pod spec 中定义、完成初始化工作的普通容器条目；pause 是运行时基础设施的一部分。
- **临时改容器文件 ≠ 修改镜像或持久部署。** 课程修改网页是验证路径；这类容器可写层改动不应成为正式发布方式，重建容器后通常丢失。未来应使用新镜像或按设计挂载配置、数据。
- **两个进程争用同一地址/协议/端口才构成本例冲突。** 共享网络使它们共用端口空间；不能抽象成任何两个相同数字的端口都绝对不允许，监听地址、协议也有影响。修改 `containerPort` 声明不会替应用改 Nginx 的监听配置。
- **没有日志不证明镜像有问题。** 29:52–29:57 的推断过强。还需看容器是否启动、日志是否写到文件、上一次退出状态、OOM、事件等；崩溃后可按场景读取 previous 日志。视频的“先事件，再应用日志”是有效起点，不是穷尽所有原因。
- **多容器时 `-c` 不一定被强制要求。** 省略时 kubectl 可能按默认容器注解或第一个容器选择；为避免看错对象，学习时显式指定更清楚。参见 [官方 kubectl exec 参数](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_exec/#options)。

### 3.3 与已有经验和 v1.22.2 环境的衔接

可将 `docker ps / exec / logs` 的经验对应到 `kubectl get / exec / logs`，但 Kubernetes 多了一层 Namespace → Pod → 容器定位。`explain` 查的是字段使用说明，`describe` 查的是某个实际对象的详情和事件，类似“配置格式帮助”与“运行状态报告”的差别。

本项目使用 containerd；课程到 Node 上执行 `docker ps` 不能作为本项目查看 K8s 容器的默认办法。优先用 kubectl；需要运行时层排障时再检查 crictl 的安装与 CRI endpoint。本文不假设这些命令已经在节点安装或执行。课程里的 Calico Pod 名称也不会照样出现在本项目的 Flannel 环境。

## 4 P16：Pod 的生命周期 1

### 4.1 课程讲解主线

**从时间轴理解生命周期（00:05–03:23）。** 课程建议把图重新画出来检验理解，先放基础设施容器，再放只在启动阶段工作的 init 容器；它们完成准备工作，之后才轮到应用容器。

**初始化的顺序和阻塞（03:23–11:08）。** 多个普通 init 按列表顺序执行，每个必须成功退出后才运行下一个。课程用返回码 0 作为成功依据，用失败后的重试解释“任务没有完成就不能进入后续阶段”。随后举 Nginx/PHP 依赖 MySQL 的例子：在 init 中循环检测条件，满足后退出，让应用开始。这里必须结合下方“连坐重跑”纠正阅读，不能原样记住时间线。

**应用容器与两种钩子（11:08–21:23）。** 普通应用容器可同时存活，课程主要面向持续服务。接着解释 postStart 和 preStop：postStart 与主进程启动可能重叠，所以不能把主进程所依赖的必需文件生成工作简单塞进 postStart；preStop 发生在发出正常停止信号之前，可用于退出前处理。钩子由 Pod 所在节点的 kubelet 协调执行。

**就绪与存活是两种问题（21:24–27:27）。** readiness 询问当前是否准备好接收流量；liveness 检测应用是否陷入需要重启才能恢复的状态。课程用“Nginx 已失效，但 tail 日志的进程仍在”说明容器存在不代表业务健康；下一节再补 startupProbe 解决慢启动问题。

### 4.2 核心区别与官方纠正

**重点纠正：失败的 init 不会默认导致全部已成功 init 从头执行。** 05:37–06:58 的“连坐”说法把两种情况混在一起。正常情况下 kubelet 重试失败的那个 init；Pod 基础设施重建等特殊情形可能导致初始化重新执行。因此初始化脚本仍应尽量幂等，但不能把“init2 失败 ⇒ init1 必重跑”当成规则。普通 init 全部成功后才进入应用阶段；`restartPolicy: Never` 时 init 失败会使 Pod 失败，P17 有补充这一例外。[官方 Init Containers 的顺序与重试行为](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/#understanding-init-containers)

**重点纠正：就绪探测不是只在启动时做一次。** 24:36–25:08 说旧版曾只探测一段时间，未给出具体版本证据。本项目 v1.22 文档已经明确探针为周期性诊断；成功后仍可能再次失败并改变就绪状态。不要把这种课程追述当作 v1.22 与 v1.29 的差异。[v1.22 官方探针说明](https://raw.githubusercontent.com/kubernetes/website/release-1.22/content/en/docs/concepts/workloads/pods/pod-lifecycle.md)

其他需要限定的点：

- 02:11–02:28 将网络、存储准备和进程回收都归给 pause 不够精确。pause 主要维持 sandbox 的共享环境；网络配置由运行时/CNI 等协作，卷由 kubelet/存储组件准备。孤儿进程与僵尸进程也不是同义词：前者失去父进程，后者已退出但退出状态尚未被回收。PID 共享仍有 P14 所述配置条件。
- 07:20–08:29 “危险操作只短暂运行就能保证安全”过强。init 的价值是将初始化工具、权限和依赖与常驻应用分离；短时存在不等于自动安全，权限和挂载仍需按具体任务限制。
- 11:29 “主容器要不间断持续运行”适合本节服务案例，不能推广到 Job 等完成后退出的任务。
- 12:34–13:26 将应用容器可同时运行、容器启动顺序、镜像并发拉取混在一起。不要依赖普通 containers 列表来规定业务启动先后；镜像并发策略也不能证明同一 Pod 的所有容器同时启动。官方说明即使允许并发拉取，也不会为同一 Pod 并行拉取多个镜像。[镜像拉取的串行与并行](https://kubernetes.io/docs/concepts/containers/images/#serial-and-parallel-image-pulls)
- 18:18–18:29 的正常停止流程不是“反复发 SIGTERM 后再强杀”的固定次数机制；需要理解宽限期。preStop 和应用收到停止信号后的退出共用宽限时间，postStart 也不保证先于主进程完成。[官方容器钩子说明](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/#container-hooks)
- readiness 失败通常影响匹配 Service 的流量选择，不等于从网络上封锁 Pod IP，也不直接等同于重启容器。liveness 的判定质量取决于探测内容，不能保证所有业务请求都正常；连续失败达到阈值后才触发相应处理。

### 4.3 与已有经验和 v1.22.2 环境的衔接

普通 init 很像部署脚本中的前置任务：先准备配置，再启动服务；返回码 0 只代表该程序报告成功，业务检查是否充分由脚本决定。它和 systemd 的前置启动步骤存在类比，但运行在自己的镜像中，数据要通过明确的共享卷等方式交接。

postStart 不能当作确定完成的前置脚本；必须先完成的工作更适合普通 init 或应用启动包装脚本。readiness 可以类比负载均衡健康检查决定“接不接流量”，liveness 则是决定“是否需要重启”的恢复机制，两者失败的后果不同。

本节普通 init、postStart/preStop、readiness/liveness 在 v1.22.2 都适用。v1.29 已有默认开启的 beta 原生 sidecar：位于 initContainers 中但设置容器级 `restartPolicy: Always`，可以持续运行；因此课程“所有 init 都退出后才能运行 app”的表述只能针对普通 init。v1.22.2 不支持这套原生 sidecar 字段，不在当前实验中照抄。[官方 sidecar 版本说明](https://v1-32.docs.kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)

## 5 P17：Pod 的生命周期 2

### 5.1 课程讲解主线

**startupProbe 解决启动与存活的时序冲突（00:00–04:48）。** 应用还没启动完，liveness 就开始判失败，可能形成反复重启。单纯加很长 initialDelay 又会推迟真正故障的检测。startupProbe 用于判定启动完成；其成功之前，readiness/liveness 不开始正常探测。三种探针按容器需要分别配置，由节点 kubelet 执行。

**复习 init，再用 DNS 等待展示阻塞（05:01–10:36）。** 课程明确补充 Pod 的 Never 重启策略例外。随后定义一个 app 容器和两个 init：第一个循环执行 nslookup 等待 myservice，第二个等待 mydb；until 的条件为失败时继续循环、成功时退出。课程通过 CoreDNS 将 Service 名称解析为地址，说明可以把外部条件转为 init 的退出条件。

**用状态和日志证明运行到了哪一步（10:36–16:24）。** 创建后 READY 0/1，STATUS Init:0/2，describe 里只有第一个 init 的启动事件；指定 init 容器取 logs，看到等待。创建 myservice 后推进到 Init:1/2，第二个 init 才启动。此段主要演示第一个依赖解除后进入第二个等待点，不将其概括为两个后端都已健康可用。

**用退出码控制初始化能否完成（16:24–23:03）。** 课程使用自制 Go 程序镜像，运行一段时间后按参数退出。退出码固定为 1 的例子反复失败；复制清单改为 0 后，init 成功结束、应用容器才运行。镜像被分配到不同节点时可能需要重新拉取，缓存属于节点本地。该实验展示退出码对流程的影响，没有验证 P16 所说的“所有 init 连坐重跑”。

### 5.2 核心区别与必要纠正

- **startupProbe 成功 ≠ Ready。** 启动探针通过只是允许后续探测进入工作；是否可接收流量仍由就绪判定决定。startupProbe 也可配置延迟和失败阈值，不能把课程“容器创建即开始”记成无条件的精确时刻。
- **BackOff 是退避等待，不是永远不再创建。** 00:55–01:00 的表述容易让人以为已停止重试；应继续看重启策略、事件与容器状态。
- **没有 livenessProbe ≠ 进程死了也不管。** 03:24–03:27 漏掉 kubelet 对容器退出的管理。真正退出仍按 restartPolicy 处理；缺少 liveness 的主要盲区是进程还在、应用却卡住的情况。没有 readiness 也不意味着创建对象当刻就绪。[v1.22 官方重启策略与三类探针](https://raw.githubusercontent.com/kubernetes/website/release-1.22/content/en/docs/concepts/workloads/pods/pod-lifecycle.md)
- **nslookup 成功 ≠ 后端可用。** 本例只检查 DNS 名称可解析；普通 ClusterIP Service 即使没有健康后端，也可能已有 DNS 记录。需要判断数据库可用时，应检查所需端口/协议或真实操作，而不是停在解析成功。Service 名称简写也受命名空间影响。[命名空间与 Service DNS](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/#namespaces-and-dns)
- **Init:1/2 ≠ READY 1/2。** 前者表示普通 init 完成进度，后者数应用容器就绪情况。本例一个 app、两个 init，所以可以同时出现 READY 0/1 与 STATUS Init:1/2。
- **普通 init 的限制不只有 readiness。** 06:37–06:47 只提不能定义 readiness；普通 init 同样不支持 lifecycle、livenessProbe、startupProbe。原生 sidecar 是另一个版本和类型问题，见 P16 差异说明。[官方普通 init 与应用容器差别](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/#differences-from-regular-containers)
- 15:08 附近将集群内访问 API Server 都概括为必须经过 kubernetes Service 太绝对；它是常见的集群内稳定入口，并非所有客户端唯一可能的网络路径。

### 5.3 与已有经验和 v1.22.2 环境的衔接

这节可以直接联系 shell 的 `until`、`sleep` 和退出状态：Kubernetes 不理解脚本真正想验证的业务，只能根据运行结果推进流程。成功标准写错，即使 exit 0 也只是“错误的检查顺利结束”。相反，条件一直不满足，Pod 卡在 Init 并不一定是调度器故障，应先查看当前 init 日志。

### 7.2 2026-10-29：Deployment 的端口声明与 RS 维护什么

**问题原意：** 用户追问 Deployment 清单声明的端口与容器应用实际监听有什么关系，以及是否能通过 Deployment 创建 RS、RS 如何形成并维护 Pod、除了数量还能维护什么。

**端口解答：** 准确路径为 `spec.template.spec.containers[].ports[].containerPort`，声明随模板进入 RS／Pod。应用真正监听由其配置、启动参数等决定，例如 Nginx 的 listen；声明不会替应用改配置或完成 Docker -p 式端口映射。省略声明不自动关闭监听端口。命名端口可被 Service 的 targetPort 等引用；数字 targetPort 直接选择 Pod 目标端口，Service port 是入口端口。若应用仍听 80、命名声明却改为 8080，依赖该名称的 Service 会指向错误目标。此为助手扩展解释，未计为用户已掌握 Service。

**变更关联：** 修改 Deployment Pod 模板中的端口声明会触发发布（正常未暂停场景），但重新启动的应用仍按自己的配置监听。改变应用端口时需同时检查真实配置、声明与服务／探针等引用。普通 Pod 的不同副本使用各自 Pod 网络环境，可各自监听 80；同 Pod 容器共享端口空间，不能据“容器不同”排除冲突。

**RS 解答：** 用户创建 Deployment 对象后，Deployment 控制器创建／管理 RS，RS 控制器按模板创建 Pod；所有读写经 API Server。RS 本身是配置和状态对象，控制器才是执行协调的程序。replicas 表示 Pod 数量，模板定义每个新 Pod 的容器、镜像、配置等；selector／标签及 ownerReferences 共同用于匹配和归属。缺少时补建、多出时缩减；不就绪并不直接等于少了一个 Pod。直接编写 RS 清单也可行，但已有 Deployment 时通常由其管理。

**职责边界：** RS 不会把现有 Pod 的每个字段持续改回模板，也不负责滚动更新。Deployment 通过新旧 RS 协调模板更新，保留历史供回滚；只改 replicas 不触发模板发布，模板改变通常对应新 RS。容器退出处理与探针由 kubelet 落实，选节点属于 Scheduler，入口及流量分配属于 Service，按指标扩缩容需另配 HPA。重建的 Pod 不继承原容器内存和临时文件，错误镜像／配置也不会被自动修正。

**来源与状态：** v1.22 官方 Deployment、Service、Pod 生命周期资料、v1.22.2 API 类型与 Nginx listen 官方说明已核对，完整链接及细节见 [暂存最新问答](../PENDING.md)。本次没有实操或新增验证，解释状态为已解答／未验证；此前复盘仍待用户回答。
